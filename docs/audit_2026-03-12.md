# Audit Report: 2026-03-12

## Scope

This audit reflects the current engineering understanding of the live four-VM stand and the follow-up enterprise foundation slice prepared in `remote-edit2`.

Audited layers:

- `VM1` ingest
- `VM2` processing
- `VM3` storage and detection
- `VM4` web and React shell

## Executive Summary

The platform already runs end to end as a real SIEM stack:

- ingest accepts data
- Redis processing is active
- writer persists into ClickHouse
- stream and batch detections exist
- web and React shell are live

The enterprise foundation slice improves the web/control-plane layer without re-platforming the full stack. It adds first-class connectors, case management primitives, entity and risk state, response actions, content bundles, saved searches, secret readiness, aggregated health, dedicated React workspaces, and now service-account machine auth for integrations.

The `2026-03-13` ingest-fabric slice extends `VM1` and `VM4` with source heartbeat, collector heartbeat, edge DLQ, replay, and native ingest operations in the React shell.

The current `2026-03-13` product slice also extends analyst UX and source onboarding with dashboard drill-down, timezone-aware timelines, larger incident queues, and a LAN discovery plane that can prepare auto-monitoring jobs for unmanaged Linux-style hosts.

## Previously Confirmed Baseline Defects

The earlier audit confirmed and tracked these issues:

1. `stream_corr` had historical processing-time behavior instead of event-time behavior.
2. Batch rule `4003` broke `siem-batch-corr`.
3. `GET /api/incidents` had an overly strict preview limit.
4. The web default ClickHouse port drifted from the live HTTP port.
5. `deps.py` had grown into a monolithic data-access layer.
6. `console.py` kept the integration catalog as hardcoded Python data.
7. Content-plane runtime still used the filesystem backend instead of a true document backend.
8. OpenAPI was disabled.

## Changes Added In The Enterprise Foundation Slice

### Fixed or improved now

- OpenAPI is enabled at `/api/openapi.json`.
- Integration catalog runtime no longer depends only on the old static route payload. The web layer now pulls integration templates from the control-plane foundation.
- The active-list save path aligns with the current `deps.py` contract.
- RBAC now covers connectors, cases, entities, response, content, and health.
- RBAC now covers audit visibility for administrative users.
- React shell now has native views for connectors, cases, and entities.
- React shell now has a native access workspace for service-account and token operations.
- Control-plane changes now generate hash-chained audit events that can be verified for tampering.
- Health aggregation now includes audit-chain state and flags invalid audit linkage as an issue.
- The control plane now supports `filesystem` and optional `postgres` storage backends through the same API surface.
- VM4 now supports scoped service accounts and one-time API token issuance for machine callers.
- Ingest now has a real edge DLQ and replay loop on `VM1` instead of only a theoretical backlog item.
- Health aggregation on `VM4` now includes live ingest-runtime status from `VM1`.
- React now has a dedicated `/app/ingest` workspace for edge runtime operations.
- Dashboard timelines now expose exact bucket windows and can pivot straight into `/app/events` or `/app/incidents`.
- Timezone formatting now applies to charts and preserved filter windows instead of leaving graph time fixed.
- Incident APIs and the React queue now support larger limits and direct time scoping.
- Synthetic smoke emitters are now suppressed from operational ingest totals, which addresses the noisy `vm1-smoke stale` false signal.
- VM4 now exposes a source discovery plane with subnet scan, candidate-source inventory, role inference, and prepared onboarding jobs.

### Added, but still intentionally lightweight

- JSON-backed control-plane persistence on VM4
- response executions with real webhook, Telegram, email, and approval-gated runtime behavior
- connector runtime with real REST pull and sqlite polling behavior
- secret-readiness inventory instead of raw secret exposure
- health aggregation across the new control-plane domains
- append-only audit visibility limited to the VM4 control plane
- backend selection for the control plane with Postgres-ready persistence logic

## Not Fixed Yet

These gaps remain open after this slice:

- Kafka ingestion backbone
- transport-wide DLQ/backpressure beyond the VM1 ingest edge
- live revalidation of `siem-processing` freshness after the updated platform-source thresholds are deployed
- provisioning and enabling the Postgres-backed transactional control plane on the live stand
- full enterprise SSO and directory integration
- directory-backed auth and federation beyond the current local service-account model
- platform-wide immutable audit beyond the VM4 control plane
- full SOAR or approval workflows beyond the current basic model
- fully automated Windows and network-device onboarding beyond the current Linux-first SSH rollout

## Current Risk Assessment

- Operational risk: medium
  The platform is usable, and the ingest edge now has a real operational DLQ, but the control plane still lives as local JSON on VM4 and does not yet have HA semantics.
- Security risk: medium to high
  Credentials already exist in internal documentation and must be rotated before any production rollout.
- Product risk: medium
  The new slice closes a meaningful enterprise gap with machine auth, but does not yet replace the need for Kafka, Postgres, and enterprise federation.

## Required Follow-Up

1. Move the control plane from local JSON to Postgres.
2. Introduce Kafka and transport-wide backpressure/replay semantics beyond the VM1 edge.
3. Replace local-only human auth with OIDC, SAML, LDAP, or AD while keeping service accounts for machine callers.
4. Provision Postgres on the stand, install the optional web dependency, and enable `SIEM_CONTROL_PLANE_BACKEND=postgres`.
5. Move live secrets behind references by default.
